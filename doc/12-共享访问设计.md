# 12 · 共享访问设计（WebDAV / SMB）

> 状态：**设计稿，未实现**。目标是把库里的视频按「分类」组织成目录，用数据库里的 `title`  
> 作为文件名，让 Infuse / nPlayer / Kodi / Windows 资源管理器 / macOS Finder 这类原生客户端  
> 直接挂载播放，而不是只能开网页。
>
> 结论：**WebDAV 值得做，SMB 不该由本项目实现**（理由见第 6 节）。

## 1. 需求拆解

| 需求         | 说明                                                 | 可行性              |
| ---------- | -------------------------------------------------- | ---------------- |
| 按分类建目录     | 目录名 = `category.name`，顺序 = `category.sort`         | 虚拟目录即可，零成本       |
| 文件名用 DB 标题 | 落盘名是 `20260926133251_77d567a6.mp4`，对外必须是 `沙丘2.mp4` | 需要「路径 → 记录」的映射层  |
| 继承权限       | 用户只能看到 `07-权限模型.md` 允许的分类/视频                       | 虚拟目录天然可做，SMB 做不到 |
| 能拖动进度条     | 必须支持 HTTP `Range`（206）                             | 见 4.3，是唯一有技术风险的点 |
| 只读         | 不通过共享改文件、删文件                                       | 首版强约束，写入放 P1     |

一句话：这本质上是**把 `video` 表投影成一棵虚拟文件树**，不是「把 storage 目录共享出去」。

## 2. 方案选型

### 2.1 方案 A：进程内虚拟 WebDAV（推荐）

在现有 FastAPI 里挂一个 WebDAV 端点 `/dav`，用 `WsgiDAV` 做协议解析，自己实现  
「虚拟文件系统」Provider（根目录 / 分类目录 / 视频文件三类资源，全部由 DB 驱动）。

- 优点：用户体系、权限模型、分类、标题全部现成；零额外进程；随主程序启停。
- 缺点：文件内容要经 Python 转发，大文件吞吐不如原生文件服务；Range 需实测。
- 依赖：`wsgidav>=4.3`、`a2wsgi>=1.10`（WSGI → ASGI 适配）。

### 2.2 方案 B：影子目录 + 外部 DAV 服务（备选）

脚本把 `storage/videos/**` 以**硬链接**方式铺成一棵真实目录树  
`storage/_share/<分类>/<标题>.mp4`（NTFS/ext4 同卷硬链接，不占额外空间），  
再用 `rclone serve webdav --read-only` 或 Caddy 的 webdav 模块对外提供。

- 优点：文件由成熟服务器直接发送，Range/并发/吞吐都是工业级；代码量极小（一个同步脚本）。
- 缺点：**无法按用户做权限**（一套目录只能对应一个账号）；每次改标题/分类都要重建索引；  
  ReFS、跨卷、部分 NAS 不支持硬链接，只能退化成复制（浪费空间）。
- 定位：只给「受信任局域网 / 家庭影院单一账号」用的降级方案。

**建议：A 为主，B 作为 P2 的性能兜底（或在大文件吞吐不达标时切换）。**

## 3. 虚拟路径模型（方案 A）

```
/dav/                                 根（PROPFIND Depth:1 列出可见分类）
├── 电影/                              category.name（按 sort 升序）
│   ├── 沙丘2.mp4                      video.title + 原扩展名
│   └── 奥本海默.mkv
├── 电视剧/
├── 动漫/
├── 教学/
├── 未分类/                             category_id 指向已删除/不存在的记录
└── _单集/                             分类不可见、但被 user_video_rule.allow=1 单独放行的视频
```

规则：

1. **根目录成员** = 当前用户 `compute_visible_category_ids()` 的结果 ∩ `category.status=1`  
   （管理员不过滤，且可见隐藏分类，便于核对）。空分类默认不显示，可由  
   `webdav.hide_empty_category` 控制。
2. **分类目录成员** = 该分类下 `status=1` 且未被 `user_video_rule` 拉黑的视频。
3. **单独放行**的视频如果所属分类不可见，落在 `_单集/`，避免通过目录名泄漏隐藏分类的存在。
4. 路径分隔符统一 `/`；`.` 和 `..` 段一律拒绝（防穿越），解析后还要校验  
   `Path(abs).resolve().is_relative_to(storage_root)`——复用 `ingest_service._rel` 的同款校验。
5. 三个真实目录 `chunks/ tmp/ logs/` 永远不出现（它们本就不在 `video.path` 里，天然隔离）。

## 4. 关键实现点

### 4.1 文件名映射（核心）

落盘名不可读，对外名必须来自 `title`。清洗规则（按 Windows 最严格标准，保证跨平台一致）：

```python
def safe_name(title: str, max_len: int = 80) -> str:
    s = re.sub(r'[\\/:*?"<>|\x00-\x1f]', "_", title).strip()
    s = re.sub(r"\s+", " ", s)
    s = s.rstrip(". ")                       # Windows 不允许结尾空格/点
    if not s or s in {".", ".."}:
        s = ""
    if s.upper().split(".")[0] in RESERVED:  # CON PRN AUX NUL COM1-9 LPT1-9
        s = "_" + s
    return s[:max_len]                       # 中文 3 字节/字，80 字 ≈ 240B，留出扩展名余量
```

- 扩展名取 `Path(video.path).suffix`，缺失时按 `video.mime` 反查。
- **重名**：同一分类内标题可能重复（不同集数用了同一个标题）。按 `video.id` 升序，  
  第一个保持 `标题.mp4`，后续依次 `标题 (2).mp4`、`标题 (3).mp4`。确定性可复现。
- **反向解析**（`标题 (2).mp4` → `video.id`）：不要靠猜。做法是按分类懒加载一张  
  `{对外名: video_id}` 索引表，用 `max(video.updated_at)` 做版本戳，进程内缓存  
  `webdav.cache_ttl_seconds`（默认 60s）。命中不了再回源一次 DB（单分类一次  
  `SELECT id,title,path FROM video WHERE category_id=? AND status=1 ORDER BY id`，  
  千行级，毫秒级）。
- 索引缓存命中率极高：客户端总是先 `PROPFIND` 再 `GET`，名字一定是刚列出来的。

### 4.2 资源类（WsgiDAV Provider）

```python
class DavRoot(DAVCollection):      # /
    def get_member_names(self):    # 可见分类名 + "_单集"
    def get_member(self, name):    # -> DavCategory

class DavCategory(DAVCollection):  # /电影
    def get_member_names(self):    # 该分类下对外文件名列表
    def get_member(self, name):    # -> DavVideo
    get_last_modified = category.updated_at
    get_etag         = md5(f"cat:{id}:{updated_at}")

class DavVideo(DAVNonCollection):  # /电影/沙丘2.mp4
    support_ranges  = True
    is_collection   = False
    def get_content_length(self):  # video.size
    def get_content_type(self):    # video.mime
    def get_etag(self):            # md5(f"{id}:{size}:{updated_at}")
    def get_content(self):         # 打开 storage 下的真实文件（流式，勿 read() 全量）
    def begin_write(self, ...):    # read_only=True 时抛 DAVError(403)
    def delete/rename/move:        # 同上，403
```

`etag` 一定要做——播放器会用 `If-None-Match` 跳过重复请求，也让 304 生效。

### 4.3 Range / 大文件（唯一的技术风险点）

- `HEAD` 必须返回正确 `Content-Length`，否则 Infuse/VLC 会判定文件损坏。
- `GET` 必须支持 `Range: bytes=...` → `206` + `Content-Range`，否则**不能拖动进度条**，  
  4K 片子基本没法看。
- WsgiDAV 4.x 对 `support_ranges=True` 的资源有内置实现，但版本间行为有差异。  
  **落地时必须实测**：4GB 以上 mp4 + `curl -r 1000000-1000999` + Infuse 拖进度条。  
  不达标就在 Provider 里覆写 `RequestServer.do_GET`，自己写 206 分支（代码约 60 行，  
  按 1MB 块读文件，禁止整文件入内存）。
- 吞吐预期：经 Python WSGI 转发，单流大约 100–250 MB/s，局域网千兆（理论 110MB/s）  
  够用；万兆/多路 4K 并发不要指望，那是方案 B 的领域。

### 4.4 认证与性能陷阱

- 认证由自定义 `BaseDomainController` 完成：查 `sys_user`，`verify_password` 校验，  
  `status=1` 才放行，把 `user_id` 塞进 `environ` 供 Provider 算可见性。
- **坑**：`hash_password` 是 PBKDF2 12 万轮，单次校验约 30–60ms。Windows 资源管理器  
  和 macOS Finder 每个请求都会重新认证，一个深度 1 的目录浏览就能打出几十次校验。  
  必须加一层 `{sha256(username+password): user_id}` 的 LRU 缓存（60s），  
  否则挂载后目录会「一卡一卡地加载」。
- 建议同时支持「用户名 + 专用令牌」：`sys_user` 加一列 `dav_token`，或允许把 JWT 当密码。  
  客户端（尤其 Infuse）习惯把密码明文存在设备上，专用令牌可单独吊销，不牵连登录密码。
- 禁用账号、改密码后必须让缓存失效（缓存 key 含密码散列，改密即天然失配）。

### 4.5 客户端怪癖（决定「能不能用」）

| 客户端                                 | 可用性        | 注意                                                                                                                                      |
| ----------------------------------- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Windows 资源管理器（映射网络驱动器）              | 可用，需配置     | 必须启动 `WebClient` 服务；HTTP 下默认拒绝 Basic 认证，需改注册表 `HKLM\SYSTEM\CurrentControlSet\Services\WebClient\Parameters\BasicAuthLevel=2`，或前面套 HTTPS |
| macOS Finder（前往 → 连接服务器）            | 可用         | 会尝试写 `.DS_Store` / `.Trashes`，只读会报 403 弹窗。建议对 `.DS_Store`、`.Trashes`、`._*` 的写入**直接返回成功并丢弃**，体验干净                                        |
| Infuse / nPlayer / VLC（iOS/Android） | 可用         | 首选场景，WebDAV + Range 完美，海报墙靠文件名匹配                                                                                                        |
| Kodi                                | 可用         | WebDAV 源，注意先关闭「使用本地缓存」避免整片下载                                                                                                            |
| Windows PotPlayer                   | 不支持 WebDAV | 需要 RaiDrive / Mountain Duck 之类的桥接盘符                                                                                                     |

Windows 桌面端体验想省事：**加一层 HTTPS 反向代理（Caddy 一条配置）**，比改注册表靠谱，  
也能避免密码明文过网。

## 6. 为什么不做 SMB

明确反对在项目内实现 SMB 服务端，五个理由，第一条是致命的：

1. **SMB 协议无法表达「虚拟文件名」。** SMB 返回的是真实文件系统对象，服务端没有  
   「把这个 inode 显示成另一个名字」的机制（不像 WebDAV 是资源抽象，你想叫什么都行）。  
   要实现「按标题命名」，文件在磁盘上就必须真的叫那个名字——也就是说必须先物化一棵  
   目录树，那么 SMB 只是「共享一个已经整理好的真实目录」，跟本项目没本质关系。
2. **没有可用的 Python SMB 服务端。** `impacket.smbserver` 是研究/演示级实现  
   （oplock、leasing、并发、大文件性能都很弱），暴露在局域网上等于开一个未加固的  
   445 端口。生产不可用。
3. **端口冲突。** Windows 主机的 445 已被系统 SMB 服务占用，无法二次监听。
4. **吞吐。** 4K 播放要的是零拷贝/内核直发，Python 转发做不到；而 SMB 又要求它必须转发。
5. **认证模型不兼容。** SMB 认证走 NTLM/Kerberos，与现有 `sys_user` + PBKDF2 体系对不上，  
   最终只能退化成「OS 账号 + ACL」，`user_category_rule` 那一整套权限逻辑全部失效。

**如果确实需要 SMB**（例如某些只认 SMB 的电视盒子），正确做法是「不做代码，做共享」：

```powershell
# 1) 用脚本把虚拟命名物化为硬链接树（同卷 NTFS，不占额外空间）
python scripts/sync_share_tree.py --dest storage/_share

# 2) 交给 Windows 原生 SMB 共享，权限由 OS ACL 管
New-SmbShare -Name Media -Path D:\Program\repository\media_manager\storage\_share -ReadAccess Everyone
```

代价必须提前说清：**权限粒度退化为「能访问这台机器的人都能看全部视频」**，  
且每次改标题/分类都要重跑同步脚本（或加文件监听）。

## 7. 决策汇总

| 选项               | 权限         | 命名映射 | 性能   | 复杂度 | 结论        |
| ---------------- | ---------- | ---- | ---- | --- | --------- |
| WebDAV（方案 A，进程内） | 完整继承 DB 权限 | 原生支持 | 千兆够用 | 中   | **采用**    |
| WebDAV（方案 B，影子树） | 无（单账号）     | 需物化  | 极佳   | 低   | 降级备用      |
| SMB（自研）          | —          | 不可能  | —    | 高   | **否决**    |
| SMB（原生共享影子树）     | 仅 OS ACL   | 需物化  | 极佳   | 低   | 特定硬件需要时才用 |
