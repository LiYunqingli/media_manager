# 05 · 分片上传设计

对应需求 9：「管理端视频上传需要使用高明的方式，例如分片，全程都需要能够看到进度，
例如分配进度，上传进度，视频合并进度等等。」

## 1. 为什么是"前端切片 + 服务端合并"

需求明确要求由 JS 切片。相比服务端流式追加，前端切片换来四个能力：

1. **并发**：多片同时传，充分利用带宽；
2. **可恢复**：断网/刷新后只需重传缺失分片，而非整个文件；
3. **可分片校验**：每片可带 MD5，坏片单独重传；
4. **可见的分片级进度**：管理端能把每个分片渲染成一个小方格实时点亮。

代价是服务端要做一次完整文件的磁盘拼接。在本项目规模下（教学/演示环境）这个开销完全可接受。

## 2. 整体协议

```
┌──────────┐                                    ┌──────────────┐
│  浏览器   │                                    │   FastAPI    │
└────┬─────┘                                    └──────┬───────┘
     │ 1. 计算文件特征值(名字+大小+首1MB 的 SHA-256)       │
     │ ────────────── POST /upload/init ───────────────►│
     │ ◄── { upload_id, chunk_size, total_chunks }      │  写 upload_session
     │     (命中 file_hash 时直接 instant=true 秒传)      │
     │                                                   │
     │ 2. GET /upload/{id}/progress?with_indexes=true    │
     │ ◄── { uploaded_indexes: [0,1,2] }                │  跳过已传分片
     │                                                   │
     │ 3. 并发(默认3) POST /upload/chunk (multipart)      │
     │ ────────── upload_id, index, file ──────────────►│  写 chunks/<id>/<i>.part
     │ ◄── { uploaded_chunks, percent, speed, ... }     │  写 upload_chunk
     │     (可重复上报同一 index，覆盖即可)                │
     │                                                   │
     │ 4. POST /upload/{id}/merge  {category_id,title}   │  提交后台线程
     │ ◄── { stage: "merging" }（立即返回）               │
     │                                                   │
     │ 5. WS /ws/admin/upload/{id}?token=…               │  ┌─ merging: 顺序拼接
     │ ◄── 进度帧(0.2~2s 自适应) ────────────────────────│  ├─ probing: 探测元信息
     │     或轮询 GET /upload/{id}/progress              │  ├─ covering: 抽帧封面
     │                                                   │  └─ 写 video 表 → finished
     │ ◄── { stage:"finished", video_id: 12 }           │
```

## 3. 阶段与进度模型

单一百分比 `percent` 由四个阶段映射而成，保证进度条连续不跳变：

| 阶段 | 区间 | `percent` 计算 | 对应 UI 文案 |
| --- | --- | --- | --- |
| `init` | 0 | 0 | 已分配上传任务 |
| `uploading` | 0 → 70 | `uploaded_chunks / total_chunks × 70` | 分片上传中 |
| `merging` | 70 → 90 | `70 + merged_bytes / total_size × 20` | 分片合并中 |
| `probing` | 90 → 95 | 阶段进度常量 | 解析视频信息 |
| `covering` | 95 → 100 | 阶段进度常量 | 生成视频封面 |
| `finished` | 100 | 100 | 处理完成 |
| `failed` | — | 保留失败时的值 | 处理失败 |

映射实现在 `app/services/upload_service.py` 的 `STAGE_RANGE` 与 `_stage_percent()`。
"分配进度"体现在 `init` 阶段返回的 `total_chunks` —— 前端据此渲染出全部分片格子，
此时虽未开始传输，但"要传多少、每一片多大"已经明确可见。

## 4. 进度为什么放在数据库

`upload_session` 表承载全部进度状态，而不是放在进程内存。换来三件事：

1. **刷新页面不丢进度**：重新打开管理端就能看到进行中的任务；
2. **多通道一致**：HTTP 轮询与 WebSocket 推送读的是同一份快照，不存在两套状态；
3. **多进程安全**：`--workers 4` 部署时，合并线程在 A 进程、轮询请求命中 B 进程也能正确返回。

代价是合并过程中会频繁 `UPDATE`。因此写库按 `upload.progress_interval_ms`（默认 300ms）节流，
而不是每读一个分片就写一次。

## 5. 断点续传

关键在于**服务端持久化分片清单**：

- 每片落盘成功后在 `upload_chunk` 插入一条 `(upload_id, chunk_index, size)`；
- 前端在 `init` 之后先请求 `progress?with_indexes=true`，拿到 `uploaded_indexes`；
- 上传任务队列 = `[0, total_chunks)` 减去 `uploaded_indexes`，只传缺失的；
- 分片落盘使用「写 `.tmp` → `os.replace()` 原子改名」，避免半截文件被误认为已完成。

因此：断网、关浏览器、甚至重启后端，重新选择同一个文件继续上传都只会补缺失的分片。

前端实现见 `frontend/static/js/uploader.js` 的 `_resumeUpload()`。

## 6. 秒传

`init` 请求里带 `file_hash`（前端用 `crypto.subtle.digest('SHA-256')` 对
「文件名 + 大小 + 最后修改时间 + 文件首 1MB」做摘要，避免大文件全量哈希的耗时）。

服务端查询：

```sql
SELECT v.id, v.title, v.path, v.size
FROM upload_session u JOIN video v ON v.id = u.video_id
WHERE u.file_hash = %s AND u.stage = 'finished' AND u.video_id > 0 LIMIT 1
```

命中则直接返回 `instant=true` 与 `video_id`，前端立刻标记完成，零字节传输。

> 采用"弱哈希"是工程折中：全文件 SHA-256 在 1GB 文件上要跑十几秒，
> 而秒传只是体验优化，不是安全机制，碰撞代价仅是"误判为已存在"。
> 如需强校验，可在管理端主动上传时改用 `chunk_hash` 逐片校验（接口已支持）。

## 7. 合并实现要点

`_merge_worker()` 在 `ThreadPoolExecutor(max_workers=2)` 中执行：

1. **前置校验**：`upload.verify_chunks=true` 时先比对 `upload_chunk` 数量与磁盘文件是否齐全，
   缺失时立刻失败并列出前 20 个缺失序号（而不是拼出一个坏文件才发现）；
2. **顺序拼接**：按 `0..total_chunks-1` 依次读取，每片用 1MB 缓冲读块累加；
3. **限频上报**：每 300ms 写一次 `merged_bytes` 与 `percent`，同时计算瞬时速度；
4. **大小校验**：合并完成后比对文件大小与 `total_size`，不一致则判为失败（`code=5004`）；
5. **原子落地**：先写 `.merging` 临时文件，校验通过后 `replace()` 成正式文件；
6. **就地处理 + 入库**：交给 `ingest_service.ingest_file()` —— 与服务端目录批量导入
   （`scripts/import_videos.py`，见 [10](./10-批量导入工具.md)）**共用同一段实现**，
   避免两条入口的行为漂移。内部依次是：
    - **容器校验 / 自动转封装**：`media.auto_remux=true` 时，「真实容器与扩展名不符」
      的文件会被无损转封装（stream copy；实测 104MB 的 TS→MP4 仅 0.8s，MP4 输出带
      `movflags=+faststart`）；失败则保留原文件并在提示中说明；
    - **元信息探测**：`media_service.probe()`（三级降级，见下）；
    - **封面生成**：有自定义封面用自定义，否则抽关键帧；失败只记警告，不阻断入库；
    - **入库**：`video_repo.create()`，返回 `video_id`。

   阶段进度通过 `on_stage(stage, ratio, message)` 回调写回 `upload_session`
   （其中 `remuxing` 归入 `merging` 区间，不新增进度段）；
7. **收尾**：把 `stage` 置为 `finished`、回填 `video_id`，并把 `ingest_file` 返回的
   `notes`（如「已自动转封装」「元信息探测失败」）追加到 `message`；
8. **清理**：按配置删除分片目录与 `upload_chunk` 记录；
9. **异常兜底**：任何异常都写入 `stage='failed'` 与 `error` 字段，前端能直接看到原因。

全程用 `_RUNNING` 集合 + 锁防止同一 `upload_id` 重复触发合并。

## 8. 并发与容错

| 环节 | 措施 |
| --- | --- |
| 前端并发数 | 默认 3（管理端可调 1–6），在 `MM.ChunkUploader` 的 `concurrency` 选项 |
| 单片重试 | 失败按 800ms × 2ⁿ 退避重试，默认 3 次 |
| 分片覆盖 | 同一 `index` 重复上传直接覆盖，`upload_chunk` 用 `INSERT IGNORE`，天然幂等 |
| 分片大小 | 服务端限制 256KB–64MB；非末片超过 `chunk_size` 直接拒绝 |
| 分片数上限 | `upload.max_chunks`（默认 20000），超出提示调大分片尺寸 |
| 单请求上限 | 128MB（`_MAX_CHUNK_BYTES`），防止异常大请求打满内存 |
| 过期回收 | `POST /upload/sessions/cleanup` 按 `session_expire_hours` 清理超时会话与分片 |
| 取消 | `DELETE /upload/{id}` 删除会话与分片目录；合并中不允许取消 |

## 9. 进度通道：WebSocket 优先，轮询兜底

`app/api/ws.py` 中的实现：

```python
while True:
    snapshot = upload_service.snapshot(upload_id)
    payload  = json.dumps({"code": 0, "msg": "ok", "data": snapshot}, ensure_ascii=False)
    if payload != last_payload:        # 内容无变化不推，省流量
        await websocket.send_text(payload)
        interval = 0.2                  # 有变化 → 加密推送
    else:
        interval = min(2.0, interval * 1.5)   # 稳定 → 逐步放慢
    if snapshot["stage"] in ("finished", "failed"):
        break
    await asyncio.sleep(interval)
```

前端 `MM.ChunkUploader._openSocket()` 在连接失败或异常关闭时自动切到
`_startPolling()`（1 秒一次）。两条路径消费的数据结构完全相同，
所以无论走哪条，UI 代码都不用改。

## 10. 前端分片可视化

管理端 `frontend/admin/upload.html` 把分片渲染成小方格：

```html
<div class="chunk-grid">
  <span v-for="c in t.chunks" :key="c.i"
        class="chunk-cell" :class="{ 'chunk-cell--done': c.done }"></span>
</div>
```

- 已完成分片变绿，当前正在传的分片带脉冲动画；
- 分片数超过 400 时只渲染前 400 格（`buildChunks()` 中的 `limit`），避免 DOM 过大；
- 进入 `merging` / `finished` 阶段后全部点亮，视觉上衔接"传输完成 → 开始合并"。
