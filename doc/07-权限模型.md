# 07 · 权限模型

对应需求 10：「管理端能够单独设置用户能够看到哪些分类下的视频，并且能够单独设置黑名单，
例如允许 user1 查看分类1，但是禁止分类1下的视频1。」

## 1. 想解决什么问题

管理端需要一个**细粒度、可组合**的可见性控制：

- 粗粒度：整个分类给你看 / 不给你看；
- 中粒度：分类默认不给，但**单独放行**其中某个视频（「只给你开这一个」）；
- 细粒度：分类给你看，但**单独屏蔽**其中某个视频（需求原文的例子）。

这里刻意**不做角色/权限点（RBAC）系统**。视频站点的真实需求就是「谁能看哪些内容」，
用规则表比 RBAC 直观得多，也更容易在 SQL 层直接翻译成 `WHERE` 条件。

## 2. 模型总览

两张规则表，用 `allow` 位区分白/黑名单：

| 表 | 粒度 | `allow = 1` | `allow = 0` |
| --- | --- | --- | --- |
| `user_category_rule` | 分类 | 分类白名单 | 分类黑名单 |
| `user_video_rule` | 视频 | 视频白名单（强制放行） | 视频黑名单（强制屏蔽） |

四类规则，语义如下：

1. **分类白名单**：用户若存在任意一条 `user_category_rule.allow = 1`，
   则**只能**看到这些分类；一条都没有时，默认可看**全部启用分类**。
2. **分类黑名单**：在白名单结果上再剔除。
3. **视频白名单**：即使所属分类不可见，也**强制放行**该视频。
4. **视频黑名单**：**最高优先级**，命中即不可见。需求原文的例子就靠它。

## 3. 可见视频集合的定义

用集合语言写清楚，避免歧义：

```
设：
  C_allow  = 分类白名单集合（可能为空）
  C_deny   = 分类黑名单集合
  V_allow  = 视频白名单集合
  V_deny   = 视频黑名单集合
  C_all    = 全部启用分类（C_allow 为空时的兜底）

分类可见集合 C_visible = (C_allow 若非空 否则 C_all) − C_deny

对某个视频 v：
  若 v.id ∈ V_deny                        → 不可见（最高优先级）
  否则 若 v.id ∈ V_allow                  → 可见（绕过分类限制）
  否则 若 v.category_id ∈ C_visible       → 可见
  否则                                    → 不可见
```

管理员（`role = 'admin'`）**不受任何限制**，`Visibility.is_admin = True`，
四类规则列表全空，SQL 里第一个括号整体省略。

## 4. 优先级一览

从高到低：

| 优先级 | 规则 | 效果 |
| --- | --- | --- |
| 1（最高） | 视频黑名单 `V_deny` | 一票否决，覆盖一切 |
| 2 | 视频白名单 `V_allow` | 无视分类限制，强制可见 |
| 3 | 分类黑名单 `C_deny` | 剔除分类 |
| 4 | 分类白名单 `C_allow` | 限定可见范围 |
| 5（兜底） | 全部启用分类 | 无白名单时默认放开 |

同一「视频/分类」不允许既在白名单又在黑名单 —— 见第 7 节的写入规范化。

## 5. SQL 落地（核心）

模型的落地在 `video_repo._visibility()`，它只负责**把 ID 列表拼成 SQL 片段**，
不关心规则怎么来的：

```python
def _visibility(*, category_ids, deny_category_ids, video_allow_ids, video_deny_ids):
    sql_parts, params = [], []

    if category_ids is not None:                       # 管理员为 None，整段省略
        cat_sql, cat_params = in_clause(category_ids)
        allow_sql, allow_params = in_clause(video_allow_ids)
        # 可见 = 分类在可见集合内 或 视频被单独放行
        sql_parts.append(f"(v.category_id IN {cat_sql} OR v.id IN {allow_sql})")
        params.extend(cat_params)
        params.extend(allow_params)

    deny_cat_sql, deny_cat_params = _not_in(deny_category_ids, "v.category_id")
    sql_parts.append(deny_cat_sql)                     # AND v.category_id NOT IN (...)
    params.extend(deny_cat_params)

    deny_video_sql, deny_video_params = _not_in(video_deny_ids, "v.id")
    sql_parts.append(deny_video_sql)                   # AND v.id NOT IN (...)
    params.extend(deny_video_params)

    return " AND ".join(sql_parts), params
```

生成的最终条件形如：

```sql
-- 可见 = 分类在可见集合内 或 视频被单独放行
( v.category_id IN (<可见分类>) OR v.id IN (<视频放行>) )
AND v.category_id NOT IN (<分类黑名单>)
AND v.id NOT IN (<视频黑名单>)
```

这段 SQL 被以下查询复用（全部通过参数透传，没有一处重复实现规则）：

| 函数 | 用途 |
| --- | --- |
| `list_page` | 用户端视频列表、搜索、分类页分页 |
| `related` | 详情页「相关推荐」（同分类优先 → 热门补齐） |
| `list_by_category` | 首页分类板块、继续观看补位 |
| `list_hot` | 首页热门 |
| `list_latest` | 首页最新 |

## 6. 分页 `total` 为什么是准的

常见坑：先按可见性过滤，再用「过滤后的数量」当分页总数 —— 一旦 SQL 写错，
`total` 会在客户端暴露「有多少你看不到的视频」。

本项目的做法是：**`COUNT(*)` 与列表查询共用完全相同的 `WHERE` 子句**：

```python
clause = f"WHERE {' AND '.join(where)}"
total = db.count(f"SELECT COUNT(*) AS c FROM video v "
                 f"LEFT JOIN category c ON c.id = v.category_id {clause}", tuple(params))
rows  = db.query_all(f"SELECT {_LIST_COLUMNS} FROM video v "
                     f"LEFT JOIN category c ON c.id = v.category_id "
                     f"{clause} ORDER BY ... LIMIT %s OFFSET %s", (*params, ...))
```

因为可见性条件本身就写进了 `clause`，`total` 天然只统计可见部分，
不存在数量泄露。

## 7. 规则的写入与规范化

管理端保存走 `PUT /api/admin/users/{id}/permissions`，最终落到
`permission_service.save_rules()`。它是**覆盖式**写入（先清空再插），
并在写入前做两处规范化，防止自相矛盾的规则进库：

```python
# 同一分类不能既白又黑：白名单优先保留，从黑名单剔除
deny_cats = [c for c in deny_cats if c not in allow_cats]
# 视频黑名单优先级最高：同一视频不能同时白黑
allow_videos = [v for v in allow_videos if v not in deny_videos]
```

存储层 `permission_repo.replace_rules()` 在**同一个事务**里清空并重写两张表，
避免「清空了还没写入」的中间态被读到。

## 8. 级联清理

规则是「外键关联」的，但项目不用数据库外键（便于分片/迁移），
因此在 service 层手动清理，三个入口：

| 触发动作 | 清理函数 | 清理内容 |
| --- | --- | --- |
| 删除视频 | `cleanup_video_rule(video_id)` | `user_video_rule` 中该视频的所有规则 |
| 删除分类 | `cleanup_category_rule(category_id)` | `user_category_rule` 中该分类的所有规则 |
| 删除用户 | `cleanup_user(user_id)` | 该用户的两张规则表 + `view_session` |

> 若不清理会怎样：某视频被删后 ID 可能被复用（自增一般不复用，但换库/导数据会），
> 残留规则会「幽灵生效」。所以删除动作一律级联清理。

## 9. 管理端怎么操作

接口（`backend/app/api/admin/users.py`）：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/admin/users/{id}/permissions` | 读取用户当前全部规则 |
| `PUT` | `/api/admin/users/{id}/permissions` | 覆盖式保存规则 |
| `GET` | `/api/admin/users/{id}/permissions/videos` | 分页挑视频，附带每个视频的当前规则状态 |

`permissions/videos` 返回的每项多一个 `rule` 字段：

| `rule` | 含义 |
| --- | --- |
| `-1` | 无规则（跟随分类） |
| `0` | 已加入视频黑名单 |
| `1` | 已加入视频白名单 |

前端 `frontend/admin/users.html` 的「权限抽屉」：

- **分类区**：每个分类一个三态循环按钮（无 → 允许 → 禁止 → 无）；
- **视频区**：分页列表，每个视频一个三态 radio（跟随分类 / 允许 / 禁止）。

## 10. 走查示例

场景：`user1` 允许看分类 1，但禁止分类 1 下的视频 99。

规则表内容：

```
user_category_rule: (user1, cat=1, allow=1)
user_video_rule:    (user1, video=99, allow=0)
```

构造出的 `Visibility`：

```
category_ids     = [1]        # 有分类白名单，仅可见分类 1
deny_category_ids = []
video_allow_ids  = []
video_deny_ids   = [99]
```

SQL 条件：

```sql
(v.category_id IN (1) OR v.id IN (NULL))     -- 视为 v.category_id = 1
AND 1=1                                       -- 无分类黑名单
AND v.id NOT IN (99)                          -- 视频一票否决
```

结果：`user1` 能看到分类 1 的全部视频，**除了视频 99**。符合需求原文。

再叠加一例：给 `user1` 单独放行分类 2 下的视频 200（分类 2 本身不可见）：

```
user_video_rule: (user1, video=200, allow=1)
```

SQL 条件变为：

```sql
(v.category_id IN (1) OR v.id IN (200)) AND ... AND v.id NOT IN (99)
```

视频 200 因命中白名单而可见，其余分类 2 的视频仍不可见。

## 11. 常见排查

| 现象 | 原因 | 定位 |
| --- | --- | --- |
| 用户看不到任何视频 | 存在分类白名单但白名单里的分类被禁用 | 查 `category.status` 与 `user_category_rule` |
| 分类全部可见（以为设置了限制） | 用户**没有**任何 `allow=1` 分类记录 → 默认全放开 | 想限制就至少加一条分类白名单 |
| 视频仍然可见（以为拉黑了） | 规则被 `replace_rules` 覆盖时被规范化剔除（该视频同时在白名单） | 检查该视频是否也在白名单 |
| 用户列表数量对不上 | 分类 `status=0` 不计入默认放开范围 | 见 `compute_visible_category_ids` |

排查工具：直接查 `GET /api/admin/users/{id}/permissions`，返回的
`allow_category_ids` / `deny_category_ids` / `video_allow_ids` / `video_deny_ids`
就是规则真相。
