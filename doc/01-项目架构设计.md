# 01 · 项目架构设计

## 1. 技术选型

| 层次 | 选型 | 理由 |
| --- | --- | --- |
| 后端框架 | **FastAPI** | 原生异步、自带 OpenAPI 交互文档、依赖注入清晰；相比 Flask 更适合做文件流与 WebSocket |
| 数据库 | **MySQL 5.7+ / 8.x** | 需求指定；InnoDB 事务 + utf8mb4 支持中文与 emoji |
| 数据访问 | **PyMySQL + 手写 SQL** | 与 `sql/` 目录下的脚本一一对应，无 ORM 黑盒；连接池自实现，零编译依赖 |
| 认证 | **自实现 HS256 JWT**（标准库 hmac） | 少一个第三方依赖；PBKDF2 存密码，格式自描述便于日后升级 |
| 前端 | **原生多页 HTML + Vue 3（全局构建）** | 需求指定"原生多页"；Vue 提供响应式与组件化，同时免构建步骤 |
| 管理端 UI | **Element Plus 2.7** | 表格 / 表单 / 弹窗 / 抽屉组件成熟，适合后台 |
| 用户端 UI | **Vant 4 + 自研响应式 CSS** | Vant 提供移动端交互组件；网格与顶栏用 CSS 保证 PC 端观感 |
| 图标 | **@element-plus/icons-vue**（管理端）+ 内联符号（用户端） | 避免字体图标额外的字体文件加载 |
| 媒体处理 | **OpenCV / PyAV（自动降级）+ 纯 Python MP4 解析兜底** | 不强制外部 ffmpeg 二进制，任何环境下都能拿到时长 |

所有第三方前端库均已本地化到 `frontend/static/vendor/`，**不依赖 CDN，可完全离线运行**。

## 3. 分层职责与依赖方向

```
api  ──►  services  ──►  repositories  ──►  db(pool/session)
 │            │
 └──► schemas └──► utils（纯函数）
```

严格单向，禁止反向 import。具体约束：

- **api 层**：解析参数、取当前用户、调 service、包装 `ok()/paginated()`。**不得写 SQL，不得写业务分支**。
- **services 层**：业务规则与事务边界。可以组合多个 repo，禁止直接 `import` FastAPI 的东西（除 `UploadFile` 这种框架类型外，统一在 api 层读完再传 bytes）。
- **repositories 层**：只写 SQL，参数全部用 `%s` 占位符。不抛业务异常，不判断业务逻辑。
- **db 层**：连接池与游标生命周期。所有 PyMySQL 异常在这里翻译成 `BizError(DATABASE_ERROR)`。

好处：换数据库只动 repositories；换 HTTP 框架只动 api；写单元测试可以直接调 service。

## 4. 一次请求的完整流转

以「用户打开视频详情页」为例：

```
浏览器  GET /api/client/videos/12
   │
   ├─ deps.extract_token()        从 Authorization 头取 JWT
   ├─ auth_service.authenticate_token()   校验签名/过期，查库确认账号未被禁用
   ├─ deps.get_visibility()       permission_service 计算可见分类集合
   │
   ├─ video_service.client_detail(12, user, visibility)
   │     ├─ permission_service.get_visible_video()   403/404 判定
   │     ├─ favorite_repo.exists()                   是否已收藏
   │     ├─ history_repo.get()                       上次观看位置
   │     └─ video_repo.related()                     同分类推荐（SQL 层过滤可见性）
   │
   └─ response.ok(present_video(...))   →  {"code":0,"msg":"ok","data":{...}}
```

任何环节抛 `BizError` → 全局异常处理器 → 统一响应体 + 对应 HTTP 状态码。

## 5. 关键设计权衡

### 5.1 为什么自实现连接池而不是 SQLAlchemy

项目全部 SQL 手写（配合 `sql/` 目录的交付要求），ORM 只会多一层映射损耗与调试成本。
自实现池子约 200 行，具备保活（`ping(reconnect=True)`）、失效连接重建、归还前回滚、
池耗尽等待与超时报错，足以支撑本项目并发量。

### 5.2 为什么把上传进度持久化到数据库

进度存在 `upload_session` 表而非进程内存，带来三个直接好处：

1. 刷新页面、切换标签、重启后端，进度都不丢；
2. HTTP 轮询与 WebSocket 读到的是同一份快照，前端可任意切换而不产生不一致；
3. 多进程部署（`--workers N`）时，合并任务在 A 进程、查询请求打到 B 进程也能正确返回。

代价是合并过程中的进度写库频率需要限流，实现中按 `upload.progress_interval_ms`（默认 300ms）节流。

### 5.3 为什么用"文件切片"而非"流式追加"

需求明确要求前端切片再合并。前端切片的好处：可并发、可断点续传、可校验单片刻、
可精确展示分片级进度（本项目在管理端把分片渲染成小方格实时点亮）。
代价是要在服务端做一次完整文件的磁盘拷贝，这点开销在本项目规模下可忽略。

### 5.4 为什么可见性过滤放在 SQL 而不是 Python 后过滤

若先查全部再在内存里过滤，分页的 `total` 会失真，且大表下内存浪费严重。
本项目把可见性编译成 SQL 条件（`IN` + `NOT IN` + 白名单放行），
让 MySQL 一起参与过滤与分页，`total` 天然正确。详见 [07-权限模型](./07-权限模型.md)。

### 5.5 为什么播放器不用 `<video controls>`

原生控件无法实现需求 6 的全部交互（长按倍速、左右滑动调进度、左右半屏分别调亮度与音量）。
因此自研了一套控件层，同时保留键盘快捷键与桌面滚轮调音量等 PC 习惯。
详见 [06-播放器说明](./06-播放器说明.md)。

## 6. 前端多页组织方式

不使用打包器，改为「**一个页面对应一个 HTML + 一份内联脚本**」，
公共能力沉淀在 `frontend/static/js/`：

| 文件 | 作用 |
| --- | --- |
| `config.js` | 全局配置：接口前缀、页面路径、上传/播放器参数 |
| `utils.js` | 时间/容量/数字格式化、防抖节流、URL 工具、封面渐变占位 |
| `ui.js` | Toast / Confirm / Loading / 主题切换（无第三方依赖） |
| `request.js` | fetch 封装 + 登录态存储 + 页面级登录守卫 `MM.guard()` |
| `components-web.js` | 公共 Vue 组件（视频卡片、横向条目、空状态、骨架、分页） |
| `layout-web.js` | 用户端外壳 `web-shell`（顶栏 + 分类导航 + 搜索 + 主题 + 移动端 Tabbar） |
| `admin-common.js` | 管理端外壳 `admin-shell`（侧栏菜单 + 顶栏）与启动器 `MM.bootAdmin()` |
| `player.js` | 自研播放器 `MM.Player` |
| `uploader.js` | 分片上传器 `MM.ChunkUploader` |

**重要约定**：由于多页方案里 HTML 中的模板属于 in-DOM 模板，浏览器会先按 HTML 规则解析，
因此：

1. 自定义组件标签**必须写完整闭合标签**，禁止 `<el-option ... />` 这种自闭合写法；
2. 组件名与属性名**必须使用 kebab-case**（`<arrow-down>`、`:model-value`），
   浏览器会把标签名转小写，`<ArrowDown>` / `:modelValue` 会失效；
3. 组件内部用 JS 字符串定义的 `template`（如 `components-web.js`）走 Vue 自己的编译器，
   不受上述限制，可以正常使用自闭合标签。

## 7. 运行时路径解析

`config/config.yaml` 中的相对路径一律**相对项目根目录**（即 `backend/` 与 `frontend/` 的父目录）
解析，而不是当前工作目录。因此下面两种启动方式等效：

```bash
cd media_manager && python backend/run.py
cd media_manager/backend && python run.py
```

实现见 `app/core/config.py` 的 `Settings.resolve_path()`。
