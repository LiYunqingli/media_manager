# 02 · 数据库设计

- 数据库名：`media_manager`
- 字符集：`utf8mb4` / `utf8mb4_general_ci`
- 引擎：`InnoDB`
- 脚本位置：`sql/media_manager.sql`（基线全量）、`sql/update.sql`（增量）

## 1. 表清单

| # | 表名 | 说明 | 备注 |
| --- | --- | --- | --- |
| 1 | `sys_user` | 用户 | 系统不开放注册，账号由管理端创建 |
| 2 | `category` | 视频分类 | 支持排序与隐藏 |
| 3 | `video` | 视频 | 含时长/分辨率/码率/播放次数等元信息 |
| 4 | `user_category_rule` | 用户-分类权限 | `allow=1` 白名单 / `allow=0` 黑名单 |
| 5 | `user_video_rule` | 用户-视频权限 | 单视频放行 / 拉黑 |
| 6 | `favorite` | 收藏 | 唯一约束 `(user_id, video_id)` |
| 7 | `watch_history` | 观看历史 | 记录续播位置、累计时长、完成状态 |
| 8 | `view_session` | 播放会话 | 播放次数统计的最小单位（≥10 秒计一次） |
| 9 | `upload_session` | 分片上传会话 | 上传/合并/处理全流程进度落库 |
| 10 | `upload_chunk` | 上传分片记录 | 支持断点续传与完整性校验 |

> 命名约定：系统级表加 `sys_` 前缀（目前仅 `sys_user`），业务表用单数名词。

## 2. 表结构详解

### 2.1 `sys_user` 用户

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INT UNSIGNED PK AI | 主键 |
| `username` | VARCHAR(64) UNIQUE | 登录账号，仅允许字母/数字/`._-` |
| `password` | VARCHAR(255) | 格式 `pbkdf2_sha256$轮数$盐hex$散列hex` |
| `nickname` / `avatar` | VARCHAR | 昵称与头像 |
| `email` / `phone` | VARCHAR | 联系方式 |
| `role` | ENUM('admin','user') | 角色，决定是否能进管理端 |
| `status` | TINYINT | 1 正常 / 0 禁用（禁用的账号无法登录） |
| `remark` | VARCHAR(255) | 备注，管理端列表展示 |
| `last_login_at` / `last_login_ip` | DATETIME/VARCHAR | 最后登录信息 |

密码散列自带算法与轮数，日后升级算法可逐用户平滑迁移（登录成功时若发现旧格式则重新散列写回）。

**内置账号**（见脚本末尾 INSERT）：

| 账号 | 密码 | 角色 | 说明 |
| --- | --- | --- | --- |
| `admin` | `admin123` | admin | 系统管理员，请及时改密 |
| `user1` | `user123` | user | 演示白名单：只可见 电影/动漫/教学 |
| `user2` | `user123` | user | 默认禁用，用于验证禁用逻辑 |

### 2.2 `category` 分类

| 字段 | 说明 |
| --- | --- |
| `name` | 唯一，重复会返回业务码 5001 |
| `description` | 分类描述 |
| `cover` | 封面相对路径（相对 `storage/`） |
| `sort` | 升序排列，越小越靠前；管理端支持上下移动批量重排（步长 10） |
| `status` | 1 启用 / 0 隐藏（隐藏后用户端不可见，管理端仍可见并统计） |

### 2.3 `video` 视频

| 字段 | 说明 |
| --- | --- |
| `category_id` | 所属分类 |
| `title` / `description` | 标题与简介 |
| `cover` | 封面相对路径，空则前端用渐变占位图 |
| `path` | 视频相对路径，如 `videos/2026/09/20260926_ab12cd34.mp4` |
| `original_name` | 上传时的原始文件名 |
| `duration` | 秒（FLOAT，保留毫秒级精度） |
| `size` | 字节 |
| `width` / `height` / `bitrate` / `mime` | 探测结果 |
| `cover_source` | 0 自动抽帧 / 1 手动上传（管理端展示用） |
| `view_count` | 播放次数（**有效观看 ≥10 秒记一次**） |
| `favorite_count` | 收藏数（冗余计数，随收藏/取消同步增减，且不允许为负） |
| `sort` | 排序值，降序优先 |
| `status` | 1 上架 / 0 下架 |

索引：`(category_id, status)`、`view_count`、`created_at`，以及标题/简介的 FULLTEXT 索引。

### 2.4 `user_category_rule` 用户-分类权限

| 字段 | 说明 |
| --- | --- |
| `user_id` + `category_id` | 联合唯一 |
| `allow` | **1 = 白名单（允许）** / **0 = 黑名单（禁止）** |

语义见 [07-权限模型](./07-权限模型.md)，一句话概括：

> 只要存在任意 `allow=1`，该用户就**只能**看这些分类；
> 没有任何 `allow=1` 时，默认可看全部**启用**分类；两者都要再减去 `allow=0` 的分类。

### 2.5 `user_video_rule` 用户-视频权限

| 字段 | 说明 |
| --- | --- |
| `user_id` + `video_id` | 联合唯一 |
| `allow` | 1 = 强制放行（即使所属分类不可见） / 0 = 拉黑（优先级最高） |

典型场景（需求 10 原文）：允许 user1 查看分类1，但禁止分类1下的视频1 → 写一条
`(user1, 1, 1)` 到 `user_category_rule`，再写一条 `(user1, 视频1, 0)` 到 `user_video_rule`。

### 2.6 `favorite` 收藏

`(user_id, video_id)` 联合唯一，保证幂等收藏；`INSERT IGNORE` 实现「重复收藏不报错」。

### 2.7 `watch_history` 观看历史

| 字段 | 说明 |
| --- | --- |
| `last_position` | 上次播放位置（秒），用于续播 |
| `duration` | 上报时的视频总时长 |
| `progress` | 百分比 0–100 |
| `watch_seconds` | 累计观看秒数（增量累加，用于前端展示"累计看了多久"） |
| `finished` | 进度 ≥ `business.finished_percent`（默认 95%）视为看完 |
| `segment_id` | 最近一次播放会话 ID |

`(user_id, video_id)` 唯一，写入用 `INSERT ... ON DUPLICATE KEY UPDATE`，
其中 `watch_seconds` 是**累加**，其余字段是**覆盖**。

### 2.8 `view_session` 播放会话（播放次数统计）

`segment_id` 为前端每次进入播放页生成的随机 ID，是主键。

- 每次心跳把 `delta`（本次真实播放秒数）累加到 `watch_seconds`；
- 当 `watch_seconds >= 10` 且 `counted = 0` 时，用
  `UPDATE ... SET counted = 1 WHERE segment_id = %s AND counted = 0` 原子置位，
  受影响行数为 1 才给 `video.view_count` 加一。

这样设计解决了三个问题：**刷新页面不算新一次**、**跳着看不算**、**并发重复计数**。

### 2.9 `upload_session` 分片上传会话

| 字段 | 说明 |
| --- | --- |
| `upload_id` | PK，32 位 hex |
| `file_name` / `file_hash` | 原始文件名与整文件特征值（秒传用） |
| `total_size` / `chunk_size` / `total_chunks` | 分片参数 |
| `uploaded_chunks` | 已上传分片数（以 `upload_chunk` 为准回写） |
| `stage` | `init` / `uploading` / `merging` / `probing` / `covering` / `finished` / `failed` |
| `merged_bytes` | 合并已写入字节，用于合并进度 |
| `percent` | 整体百分比 0–100 |
| `speed` | 瞬时速度（字节/秒） |
| `video_id` | 成功后产生的视频 ID |
| `message` / `error` | 阶段提示与错误信息 |

### 2.10 `upload_chunk` 分片记录

`(upload_id, chunk_index)` 联合唯一，`INSERT IGNORE` 保证重复上报同一分片不报错。
`init` 之后前端会请求一次 `progress?with_indexes=true`，拿到已上传分片列表并跳过，
这就是断点续传的实现基础。

## 3. 实体关系

```
sys_user ──1:N── favorite ──N:1── video ──N:1── category
    │                              │
    ├──1:N── watch_history ────────┤
    ├──1:N── view_session ─────────┤
    ├──1:N── user_category_rule ───┴── category
    ├──1:N── user_video_rule ────────── video
    └──1:N── upload_session ──1:N── upload_chunk
```

> 注意：以上关系**未使用物理外键**。原因：删除分类时需要"先下架视频再删分类"的业务动作，
> 物理外键会让强制删除路径变复杂；一致性由 service 层显式保证（删除视频时联动清理
> `favorite` / `watch_history` / `user_video_rule`）。

## 4. 索引设计说明

| 索引 | 服务的查询 |
| --- | --- |
| `video(category_id, status)` | 分类页列表、首页分类板块 |
| `video(view_count)` | 热门排序、播放排行 |
| `video(created_at)` | 最新上传、趋势统计 |
| `ft_title_desc` | 标题/简介全文检索（当前实现用 `LIKE`，索引为后续替换成 `MATCH AGAINST` 预留） |
| `favorite(user_id, created_at)` | 我的收藏分页 |
| `watch_history(user_id, updated_at)` | 观看历史、"继续观看" |
| `user_category_rule(user_id)` / `user_video_rule(user_id)` | 每次请求计算可见范围（最热路径） |
| `upload_session(stage)` | 清理超时未完成会话 |

## 5. `update.sql` 使用规约（重要）

`media_manager.sql` 是**基线全量脚本，只负责从零构建，禁止再修改**。
之后所有结构或基础数据变更一律按顺序写入 `sql/update.sql`。

规则：

1. 每条变更写清 `日期 / 原因 / 变更内容`，并尽量保证**可重复执行**（如用 `IF NOT EXISTS`）；
2. `update.sql` 顶部维护 `【当前变更计数】 N / 3`；
3. **当计数达到 3 时**：把 `update.sql` 的内容整体合并进 `media_manager.sql` 的对应位置，
   调整基线使其重新成为一个可从零构建的完整脚本，然后清空 `update.sql`，计数归零。

这样保证：新人永远只需要跑一个全量脚本就能拿到最新结构，`update.sql` 也不会无限膨胀。
